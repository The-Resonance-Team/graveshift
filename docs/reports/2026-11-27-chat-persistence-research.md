# AI chat persistence and catch-up — research for design interview

Date: 2026-11-27

Status: research and recommendation, not an accepted decision or implementation.

## Recommendation

Keep PostgreSQL and the server authoritative. Use IndexedDB only as a bounded, disposable cache of a recent, server-approved `UIMessage` projection and its **server-issued, per-conversation change cursor**. On return, reauthorize, display the appropriately scoped cached projection as stale, then catch up from the cursor; replace it with an authoritative snapshot if the cursor is invalid or outside retention. Use a separate active-stream replay mechanism only if the product needs to watch a generation that is still running. This avoids making IndexedDB, browser clocks, SSE delivery, or a client-supplied message history authoritative.

## Existing Graveshift vs proposal

- The untracked [`apps/console`](../../apps/console/package.json) is a Next.js scaffold: its [home page](../../apps/console/src/app/page.tsx) is the starter page, and its dependencies contain neither `ai` nor `@ai-sdk/react`. No chat cache, catch-up endpoint, or stream resume implementation was found there. The gateway pins [`ai` 7.0.177](../../packages/gateway/package.json) but its [current interface](../../packages/gateway/src/types.ts) exposes structured `generateObject`, not a UI token stream. Current vendor docs below describe capabilities to verify against the eventual installed UI version; they are not evidence that Graveshift has them.
- [ADR 0023](../adr/0023-organization-is-the-tenant-root.md) makes Organization the tenant root and Projects its children; [ADR 0018](../adr/0018-project-scoped-state.md) retains project scope for stored rows and contracts. Server identity and membership, not a cache key, establish access. The [gateway](../ARCHITECTURE.md) owns model controls; [ADR 0022](../adr/0022-durable-model-audit.md) withholds a model result until durable audit acknowledgment. **Raw output streamed before that acknowledgment conflicts with this contract.** Default to progress/status events and publish the accepted result only after audit, or bring an explicit revised streaming/audit contract back to the owner. Do not bypass the gateway with the SDK examples' direct model calls.

## Proposed sync contract

1. **Write and order.** For each conversation, commit the canonical message/tool/run projection and an ordered change record together. Allocate a revision under a lock on that conversation's counter row in the same transaction; all writers for it must use that discipline. Expose an opaque cursor bound to the conversation, project, account/access scope, schema version and retention epoch. A change is an idempotent, versioned message upsert or deletion/tombstone, including changes to existing assistant/tool parts—not merely new messages. Batching/coalescing partial updates reduces write amplification, at the cost of a bounded amount of lost live detail after producer failure.
2. **Snapshot and delta.** Return a snapshot and high-water cursor from one consistent database snapshot; a paginated delta query returns changes after the cursor and a safe next cursor, up to a fixed high-water mark. Never advance past changes not applied. A missing, expired, schema-incompatible or mismatched cursor requires a fresh snapshot only if the request is still authorized; otherwise deny access and purge the cached view. Tombstones and retention prevent removed content from silently reappearing. Define how the recent-window membership changes: either send explicit entry/exit changes or replace the bounded window with a snapshot. Fetch older history separately.
3. **Apply.** After current identity and project access are verified, load a matching cache entry, mark it stale, and fetch deltas; reconcile by stable message ID and revision, discard duplicates, and apply deletion. Commit the projection and cursor in **one IndexedDB read-write transaction**, advancing only when that transaction completes. On failure retain the previous cursor and retry; for cache misses or errors, fetch the server snapshot. Keep local unsent drafts separate and visibly unsent; retries need a server-enforced idempotency key, not replay of a browser-asserted assistant/tool/approval history.
4. **Catch-up to live.** Either poll for durable changes while visible, or establish a live subscription that replays from the last committed cursor and then tails the same ordered log. A subscribe-first/buffer-and-deduplicate handshake followed by catch-up is another option. Never fetch a snapshot and then subscribe “from now”: a commit in between can vanish. Treat delivery as at least once and replay idempotently. Authenticate and authorize every snapshot, delta and subscription; the app must define this cursor protocol—it is **not** claimed as a built-in AI SDK `useChat` cursor API.

**Why not timestamps or a bare Postgres sequence?** Timestamps can tie, be assigned before commit, or reflect different clocks, so `(updated_at > last_seen)` can skip updates. A `nextval` is unique, but [PostgreSQL says](https://www.postgresql.org/docs/current/functions-sequence.html) its allocations are not rolled back; concurrent transactions can allocate in one order and commit in another. If a client advances past a later-committing lower number, it misses that change. A transactional, per-conversation locked counter prevents this ordering hole when every writer follows the protocol; numbers need not be interpreted by the browser. Read the snapshot and cursor from a single statement or suitable consistent transaction: [Read Committed takes a new snapshot per statement](https://www.postgresql.org/docs/current/transaction-iso.html), so unrelated sequential reads are insufficient.

## AI SDK: messages, active streams and approvals

- The [persistence guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence) recommends storing `UIMessage[]`, initializing `useChat` with saved messages, generating stable assistant IDs on the server, and validating stored tool/data/metadata parts with `validateUIMessages` before model conversion. Its `onEnd` example saves the completed response; **onEnd alone is not a durable partial-update log**. Preserve message IDs and part order; include in-progress/completed/failed/cancelled run state. For `input-streaming` tool parts, retain the full part including `rawInput` and encoding where applicable; version and migrate persisted schemas rather than blindly restoring an obsolete shape.
- The [UI stream protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol) has start/delta/end text and reasoning parts, step boundaries, tool inputs, approval events, outputs and errors. Plain text streaming cannot represent these. Do not append all updates as new messages: replace or merge a later server revision of the same message/tool call. A replay must preserve protocol semantics, including retries/reset and tool states; replaying arbitrary suffixes without the corresponding stream state can corrupt the UI.
- [Resume Streams](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams) documents `useChat`'s `resume` and its active-stream GET, plus a sample requiring application-owned active-stream tracking, `resumable-stream` and Redis. The default transport expects a **full replay**, resets the interrupted response on its start chunk, and rebuilds it. A continuation-only setting exists, but ongoing text/reasoning continuation needs the same chat instance; a reload requires full replay. This stream replay is separate from durable conversation catch-up and is not a general cursor-based history sync. Streams expire; if no active stream remains, the documented endpoint returns 204 and the client must still reconcile durable state.
- **Stop vs disconnect:** SDK docs say a resumable setup treats `stop()` and navigation as connection aborts, not cancellation of the producer. An explicit authenticated stop command must target the run/stream ID, cancel the actual gateway work, persist an authoritative partial/terminal state, and clear the active stream only conditionally on that same ID. Do not overwrite a newer server state with a client-supplied snapshot. Conversely, tying generation to the connection saves resources on disconnect but sacrifices continuous resume. `consumeStream()` can keep consumption going after disconnect, but it is not durable job execution or a crash guarantee. The sample's Next.js `after` is [bounded by route/platform duration](https://nextjs.org/docs/app/api-reference/functions/after); long work needs a producer with an appropriate lifetime and recovery strategy.
- The [tool guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage) documents server-side user approval and warns that client-supplied full history can fabricate an approval; it describes an experimental approval secret as one mitigation. For Graveshift, a displayed or cached approval is **never authority**: require an authenticated, authorized human decision against a server-stored pending request, policy and current version; make decision/execution idempotent and audit it. The user requested human approval for mutation; do not silently substitute automatic approvals. A replay or duplicate event must never execute a tool again.

## Browser lifecycle and security

- [IndexedDB transactions](https://w3c.github.io/IndexedDB/#transaction-construct) give atomic changes across scoped stores, but are short-lived; do not hold one open across network waits. The [IndexedDB spec](https://w3c.github.io/IndexedDB/#handling-versionchange) describes closing old connections on `versionchange` and handling blocked upgrades. Namespace cached data by authenticated account, Organization, Project, conversation and schema; this is collision prevention, **not** a security boundary against same-origin scripts or another person using the same browser profile.
- Persist incrementally, not only at unload. Reconcile at initial mount, `visibilitychange` to visible, `pageshow` after back/forward-cache restoration, and network recovery, with one in-flight sync per tab. [Chrome's lifecycle guidance](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) notes that hidden pages can freeze or be discarded without a final callback, and `unload` is unreliable. Treat connectivity notifications as hints and actual authenticated fetch results as truth. Limit background work; on logout/account or project switch stop streams, clear in-memory state, invalidate/purge the relevant cache, and notify other tabs.
- Use [`BroadcastChannel`](https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts) for invalidation/version hints, not sensitive message bodies or authoritative delivery. Other tabs can independently re-fetch and apply with IndexedDB transaction/version checks. An optional [Web Lock](https://w3c.github.io/web-locks/) can reduce duplicate syncing, but feature-detect it and retain a correct independent-sync fallback; frozen leaders must not block progress indefinitely. Neither mechanism replaces server idempotency or cross-device concurrency control.
- [WebKit](https://webkit.org/blog/14403/updates-to-storage-policy/) describes best-effort eviction, quota failures and optional, heuristically granted persistent storage. Bound cache size and age, catch quota/disabled/private-mode failures, and fall back to memory plus server reads. `navigator.storage.persist()` is optional and not a durability promise against user clearing. Eviction, browser/profile changes or corruption must lead to snapshot recovery, never data loss on the canonical server.
- Apply an explicit allowlist and privacy policy **before** data enters the change log, replay store, network stream or IndexedDB: chat input, model/tool output, errors, metadata, reasoning, file contents and signed URLs may contain secrets. The [SDK tool guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage#redacting-tool-errors) notes default tool errors can expose server details, and provider-executed errors have redaction exceptions; use safe tool errors and a separate authorized server-side model transcript where needed. It also warns that redacted UI tool errors can differ from the model's history and break reasoning-bound continuations. Do not assume input redaction protects output or that per-chunk filtering catches secrets split across chunks. Decide whether to buffer before release, omit sensitive part types, or use a proven streaming-safe policy; never persist provider credentials or bearer tokens in IndexedDB. Same-origin XSS can read cache and any keys available to the same script: client-side encryption with a co-located key is not an XSS defense. Offline access after revocation cannot be guaranteed erased from a disconnected device, so choose an explicit offline-display and retention policy.

## Decisions to settle in the interview

1. Is stale cached content allowed before online reauthorization, especially on shared devices or after access revocation? Safest default: no offline display until the current session and scope are verified.
2. Are status updates plus an audited final answer sufficient, or should ADR 0022 be revisited to permit provisional tokens before terminal audit? The latter changes safety, redaction, storage and UX contracts.
3. Must a run continue after a tab closes? If yes, choose producer lifetime, explicit stop, replay-store retention and cost limits. If no, cancel on disconnect and recover the last durable partial state.
4. Choose the recent-window size, change-log retention and snapshot fallback, partial-checkpoint frequency, and which tool/reasoning/file fields may be cached. Test concurrent commits, pagination, crash before/after commit, duplicate delivery, expired cursors, logout, revocation, quota failure, stream completion during reconnect, and stale stop/approval requests.
